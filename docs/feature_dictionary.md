# Feature Dictionary — Employee Analytics Master Dataset

Generated by `src/features.py` from the cleaned tables in `data_clean/` (never
from the raw CSVs). Output: `outputs/tables/employee_analytics_master.csv` —
**13,403 rows (one per employee), 106 columns**. Every count in this document
was verified by actually running the pipeline, not assumed.

Governing context: `CLAUDE.md`, `docs/analysis_plan.md`, `docs/decision_log.md`,
`outputs/reports/data_quality_report.md`. Read those first.

## 1. Grain and Base Population

One row per `employee_id`, built from `employees_clean.csv` restricted to
`excluded == False` (currently all 13,403 rows — the cleaning audit found zero
rows warranting exclusion; see `docs/decision_log.md`). If a future data
refresh causes `clean_data.py` to exclude rows, this master dataset will
automatically shrink to match — it is never built from the raw files.

## 2. The Leakage-Prevention Design (read this before using any feature)

Every employee gets exactly one **cutoff date**:

```
cutoff_date = exit_date                     if the employee departed
            = 2025-12-31 (WINDOW_END)        if the employee is still active
```

Every engagement wave and performance review used anywhere in this table for a
given employee satisfies `hire_date <= record_date <= cutoff_date`, checked
against the record's own **date column** (`survey_date`, `review_date`) —
**never** against `wave_number` or `review_cycle`, per
`docs/decision_log.md` DEC-002 (a review's `review_cycle` label was found to be
unreliable for a small subset of records; its `review_date` was not).

Concretely: no feature for a departed employee can reflect anything that
happened after they left. No feature for an active employee can reflect
anything after 2025-12-31. This was verified two ways, not just asserted:
1. `run_integrity_checks()` re-derives the eligible subset independently and
   asserts every row satisfies the bound (see Section 6).
2. Every eligibility filter logged 0 rows dropped for being post-cutoff or
   pre-hire, because the underlying cleaned data already contained zero such
   violations (`outputs/reports/data_quality_report.md` Section 13.2) — the
   filter is a live safety net, not dead code, and would catch a future
   regression.

## 3. One-to-Many Joins Were Never Merged Directly

`engagement_clean.csv` (up to 5 rows/employee) and `performance_clean.csv` (up
to 3 rows/employee) are each: (a) filtered to the eligible window above, (b)
**aggregated to exactly one row per `employee_id`** with an immediate
uniqueness assertion, and only then (c) left-joined onto the employee base. A
row-count assertion (`len(master) == len(base)`) follows every single merge.
The master table can structurally never contain more than one row per
employee — this was not just intended, it was checked after every join.

### 4.4 Engagement — Response-Behaviour (computed once per employee, not per dimension)

`response_flag` is recorded once per survey wave and applies to all 8
dimensions simultaneously — it is not dimension-specific. Duplicating these
four columns eight times (once "per dimension" as a literal reading of the
brief would suggest) would produce eight identical copies of the same fact.
Instead they are computed once, which is the correct, non-redundant
engineering choice, documented here explicitly since it is a deliberate
deviation from a literal per-dimension reading.

| Column | Description | Missingness |
|---|---|---|
| `engagement_n_waves_available` | Count of eligible waves (≤ cutoff, ≥ hire) — issued to the employee, responded or not. | Never missing; **0** is a known fact, not unknown, for 307 employees (see `docs/data_dictionary.md`, DQ-004/DQ-005). |
| `engagement_n_responses_available` | Count of those eligible waves where `response_flag == True`. | Never missing. |
| `engagement_response_rate` | `n_responses / n_waves`. | Null for the 307 employees with 0 eligible waves (0/0 is undefined, not 0). |
| `engagement_recent_non_response_flag` | True if the **latest eligible wave** was a non-response. | Null for the 307 with 0 eligible waves. |
| `engagement_consecutive_non_responses` | Length of the trailing (most recent) streak of consecutive non-response waves, as of cutoff. | Null for the 307 with 0 eligible waves. |
| `engagement_responder_to_nonresponder_transition_flag` | True if the employee responded in some eligible wave and then did not respond in a later one ("went dark" — hypothesis SR-3). | Null (undefined with <2 points) for 1,611 employees = 307 with 0 waves + 1,304 with exactly 1 eligible wave (verified exact match). |

### 4.5 Engagement — Per-Dimension Score Trajectory (×8 dimensions)

Applied identically to: `manager_effectiveness`, `psychological_safety`,
`recognition`, `career_development`, `senior_leadership_trust`,
`purpose_meaning`, `wellbeing`, `confidence_in_role_future`. All computed only
over that employee's **responded** scores within the eligible window, ordered
by `wave_number` (safe here — only used as an ordinal x-axis for an
already-time-filtered set of points, not as a leakage boundary).

| Suffix | Description | Missing when |
|---|---|---|
| `_latest_score` | Most recent available (responded, ≤ cutoff) score. | 0 responses (813 employees = 307 zero-wave + 506 surveyed-but-never-responded, verified exact match to the audit's "always dark" count). |
| `_earliest_score` | Earliest available score. | Same as above. |
| `_abs_change` | `latest − earliest`. | <2 responses (2,246 employees). |
| `_slope_per_wave` | OLS slope of score vs. `wave_number` across all available responses. | <2 responses. |
| `_volatility` | Sample standard deviation (`ddof=1`) of available responses. | <2 responses. |
| `_persistent_low_flag` | True if **≥2** available responses are ≤2 on the 1–5 scale (documented threshold: below the scale midpoint of 3). A single low score is not "persistent" by construction. | 0 responses (**not** false-by-default — genuinely unknown when there is no data at all). |
| `_consecutive_deterioration_flag` | True if there exist ≥2 consecutive wave-over-wave declines (a genuine multi-step downward run, distinct from a single dip already captured by `_abs_change`). | <2 responses. |

### 4.6 Performance

| Column | Description | Missing when |
|---|---|---|
| `performance_n_reviews_available` | Count of eligible reviews (≤ cutoff, ≥ hire). | Never missing; 0 is known for 109 employees. |
| `performance_latest_rating` | Rating from the most recent eligible review (by `review_date`, never `review_cycle` — DEC-002). | 0 reviews (109 employees). |
| `performance_previous_rating` | Rating from the second-most-recent eligible review. | <2 reviews (1,860 = 109 + 1,751 one-review employees, verified exact match). |
| `performance_rating_change_ordinal` | `latest − previous` on a 1–5 ordinal encoding (Unsatisfactory=1 … Outstanding=5). | <2 reviews. |
| `performance_goal_achievement_latest` | `goal_achievement_score` from the latest eligible review. | 0 reviews. |
| `performance_goal_achievement_trend` | OLS slope of `goal_achievement_score` across eligible reviews in chronological order. | <2 reviews. |
| `performance_promotion_recommendation_count` | Count of eligible reviews with `promotion_recommendation == True`. | Never missing (0 is known). |
| `performance_promotion_recommendation_rate` | Count ÷ `performance_n_reviews_available`. | 0 reviews. |
| `performance_promotion_recommendation_ever` | True if the count is >0. | 0 reviews. |

**Note on the missing 2025-H2 cycle** (`docs/data_dictionary.md`): because
filtering uses `review_date` and the cycle is structurally absent from the
export, `performance_latest_rating` for a still-active, long-tenured employee
may reflect a review up to ~1 year stale. This is a data-coverage limitation,
not a pipeline defect — flagged again in Section 7.

### 4.7 Outcome Labels — NEVER USE AS PREDICTORS

**Every column in this section is derived from `attrition_log.csv`, which is
recorded at or after the exit event.** They describe what already happened;
none of them can be known before an employee leaves, and none of them appear
anywhere in Sections 4.2–4.6. See Section 5 for the full leakage examination.

| Column | Definition | n=True / non-null |
|---|---|---|
| `departed` | `status == 'departed'` | 1,400 |
| `voluntary_exit` | `departed AND exit_type == 'voluntary'` | 1,133 |
| `regrettable_exit` | `departed AND regrettable_flag == True` | 153 |
| `regrettable_voluntary_exit` | `voluntary_exit AND regrettable_flag == True` | 153 |
| `pull_exit` | `departed AND pathway == 'pull'` | 445 |
| `exit_type`, `pathway`, `stated_exit_reason`, `performance_band_at_exit` | pass-through from `attrition_log.csv`, descriptive only | null for all 12,003 active employees |

**Verified empirical finding:** `regrettable_exit` and `regrettable_voluntary_exit`
are **identical** in this dataset (153 = 153) — every exit HR flagged
`regrettable_flag == True` is also `exit_type == 'voluntary'`; there are zero
regrettable involuntary exits (confirmed via cross-tab, not assumed). Both
columns are still provided as separate, independently-computed labels rather
than collapsed into one, so this equality remains a verifiable, re-checkable
fact rather than a hard-coded assumption — a future data refresh that broke
this equality would be caught, not silently hidden. Similarly, `pull_exit` is
computed independently, but it is a verified fact of this data that `pathway
== 'pull'` never co-occurs with `exit_type == 'involuntary'` (0 of 267
involuntary exits are `pull`).

## 5. Critical Examination: Which Retrospective Fields Are Outcome-Only?

Per `CLAUDE.md` Section 18 and the explicit instruction governing this module,
every field in `attrition_log.csv` was examined for whether it could ever be
known *before* an employee's exit (and therefore could be a legitimate
predictor) or only *at or after* the exit (and therefore must be outcome/
descriptive-only).

| Field | When is it known? | Used as predictor? | Used as outcome/descriptive? |
|---|---|---|---|
| `exit_type` | At the exit event | **No** | Yes — defines `voluntary_exit` |
| `regrettable_flag` | Recorded by HR after departure (retrospective judgement, `CLAUDE.md` Section 6) | **No** | Yes — defines `regrettable_exit` / `regrettable_voluntary_exit` |
| `pathway` | Derived from exit interview/HR classification, after departure | **No** | Yes — defines `pull_exit` |
| `stated_exit_reason` | Recorded at the exit interview | **No** — brief states 40–60% do not reflect the true driver even as description, let alone prediction | Yes, descriptive only, carried through with the reliability caveat |
| `performance_band_at_exit` | HR's retrospective judgement at exit | **No** | Yes, descriptive only |
| `notice_period_served` | Known only once the employee has already given notice | **No** | **Not included** in the master table at all — adds no descriptive value beyond what `exit_type`/`pathway` already carry, and including it invites misuse as a near-outcome predictor |
| `salary_at_exit` | Identical to `employees.csv.salary` for the same employee (verified, 0 mismatches) | **No** — use `salary` (Section 4.2), a genuine pre-exit field | **Not included** separately — would be a pure duplicate of `salary` for departed employees only |
| `manager_id_at_exit` | Manager at the time of departure — may differ from current `manager_id` for long-tenured stayers, but for departed employees is only known at exit | **No** | **Not included** — `manager_id` (current/last manager, Section 4.1) is the field available pre-exit and is what any predictive or manager-effect analysis should use |

**Conclusion: zero fields from `attrition_log.csv` are used as predictors
anywhere in Sections 4.2–4.6.** The only columns sourced from that file are
the five boolean outcome labels plus four purely descriptive fields, all
isolated in Section 4.7.

## 7. Known Limitations

- **2025-H2 performance gap**: `performance_latest_rating`/
  `performance_goal_achievement_latest` for currently-active employees may be
  up to ~1 year stale, since that cycle does not exist in the source data.
- **HiPo/CP-series promotion history**: no true longitudinal level-change
  event exists in the source data (`employees.csv.role_level` is a single
  current-state snapshot). `performance_promotion_recommendation_*` is the
  best available proxy for progression signal, not a direct measure of actual
  advancement — consistent with the feasibility caveat already flagged in
  `docs/analysis_plan.md` Phase 0 for hypotheses CP-1/CP-2/CP-4.
  `role_level` itself is included as a static characteristic (Section 4.2)
  but does not tell you whether or when someone was promoted *into* it.
  Actual promotion events are not derivable from this data.
- **Unexplained zero-engagement-wave employees**: 168 of the 307 employees
  with `engagement_n_waves_available == 0` are not fully explained by
  hire/exit timing alone (`docs/decision_log.md` DEC-006) — treat their
  missing engagement history as a documented gap, not a confirmed
  missing-at-random pattern, in any analysis that leans on it.
- **`stated_exit_reason` reliability**: carried through as descriptive-only
  per Section 5, but the brief's own 40–60% unreliability caveat applies to
  any use of it, including purely descriptive narrative.
- **Slope/trend features with few points**: `_slope_per_wave` and
  `performance_goal_achievement_trend` are computed from as few as 2 points
  for a large share of employees (short-tenured hires, or those near either
  end of the observation window) — a 2-point "trend" has no ability to
  distinguish signal from noise. Sample-size-aware use is the caller's
  responsibility (`CLAUDE.md` Section 12); `engagement_n_responses_available`
  / `performance_n_reviews_available` are provided specifically so every
  downstream analysis can apply its own minimum-n threshold rather than
  trusting a trend blindly.
- **Nullable boolean columns round-trip through CSV as `True`/`False`/empty
  string**, which pandas reads back as `object` dtype with a `DtypeWarning`
  unless a dtype is specified — expected CSV behaviour (no native nullable
  boolean type in CSV), not a data error. Affects: `_persistent_low_flag`,
  `_consecutive_deterioration_flag` (×8 each), `engagement_recent_non_response_flag`,
  `engagement_responder_to_nonresponder_transition_flag`,
  `performance_promotion_recommendation_ever`, `tenure_months_raw_reliable_flag`,
  `compa_ratio_outside_screening_band`.
- **No hypothesis testing, modelling, or financial costing has been performed
  on this table** — building it is Phase 0 of `docs/analysis_plan.md`; Phase 2
  (hypothesis testing) is a separate, later step.

## 8. Reproducibility

`python src/features.py` from the project root regenerates
`outputs/tables/employee_analytics_master.csv` and `outputs/logs/features.log`
from scratch every time, reading only from `data_clean/` (itself regenerated
by `python src/clean_data.py` from the untouched raw CSVs). No manual editing
of any intermediate or output file.
